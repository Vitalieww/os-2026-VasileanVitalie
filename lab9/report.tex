\chapter{INTRODUCTION AND GOAL}

\section{Introduction}
In modern operating systems adhering to the POSIX specification, user applications execute within unprivileged CPU rings (Ring 3 on x86\_64) and are isolated from direct hardware interaction by hardware memory management units (MMUs). Any interaction with peripheral storage, terminal consoles, or IPC pipes requires crossing the hardware privilege boundary into kernel space (Ring 0) via standardized system calls.

While high-level programming interfaces provide abstract wrappers (such as \texttt{printf}, \texttt{fopen}, and \texttt{fread} in the C standard library), these routines ultimately decompose into fundamental kernel system calls (\texttt{openat}, \texttt{write}, \texttt{read}, \texttt{close}). The \texttt{strace} diagnostic utility leverages the Linux kernel's \texttt{ptrace} debugging interface to intercept, decode, and log every system call issued by a process, providing complete transparency into the runtime user-kernel dialogue.

\section{Lab Objective}
The primary objective of this laboratory work is to inspect and analyze the low-level system call interface of Linux using \texttt{strace}. Specifically, the work covers:
\begin{itemize}
    \item tracing the execution of standard GNU utilities (\texttt{ls -l}) and identifying exact system calls responsible for directory examination and terminal output;
    \item developing a standalone C program (\texttt{syscalls.c}) that interacts directly with the kernel using core POSIX file descriptor system calls (\texttt{open}, \texttt{write}, \texttt{read}, \texttt{close});
    \item evaluating the POSIX file descriptor allocation policy and explaining why initial open operations return descriptor \texttt{3};
    \item analyzing the relationship between user-space buffering libraries (\texttt{printf}) and kernel-level output routines (\texttt{write}).
\end{itemize}

\section{Answers to Required Observation Questions}
\begin{enumerate}
    \item \textbf{System Call Used to Display Text:}
    The \texttt{ls} utility employs the \textbf{\texttt{write}} system call to transmit formatted directory listings to the terminal console:
    \begin{lstlisting}[language=bash]
    write(1, "total 28\n-rw-rw-r-- 1 vitalie vi"..., 385) = 385
    \end{lstlisting}
    Before writing, \texttt{ls} opens the directory stream via \texttt{openat(AT\_FDCWD, ".", ...)} and queries directory content records using the \texttt{getdents64} system call.

    \item \textbf{File Descriptor Passed to \texttt{write}:}
    The file descriptor number passed to the call is \textbf{\texttt{1}}, representing standard output (\textbf{\texttt{stdout}}).
\end{enumerate}

\chapter{PART 2: DIRECT SYSTEM CALL INTERFACES}

\section{Implementation of \texttt{syscalls.c}}
To contrast high-level library abstractions with direct kernel interfaces, the program \texttt{syscalls.c} was implemented. The application performs file creation, byte writing, file reopening, and data reading using low-level POSIX primitives:

\begin{lstlisting}[language=C]
// syscalls.c - open, write, read and close using POSIX system calls
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    const char *msg = "hello, kernel\n";

    // open() is a system call: requests a file from the kernel, returns descriptor
    int fd = open("note.txt", O_CREAT | O_WRONLY | O_TRUNC, 0644);
    if (fd < 0) { 
        perror("open"); 
        return 1; 
    }
    printf("open returned descriptor %d\n", fd);

    // write() is a system call: transfers bytes into kernel buffer cache
    ssize_t n = write(fd, msg, strlen(msg));
    printf("write sent %zd bytes\n", n);
    close(fd);

    // read it back through the kernel
    fd = open("note.txt", O_RDONLY);
    if (fd < 0) { 
        perror("open"); 
        return 1; 
    }
    char buf[64];
    n = read(fd, buf, sizeof(buf) - 1);
    if (n >= 0) {
        buf[n] = '\0';
    }
    printf("read got %zd bytes: %s", n, buf);
    close(fd);

    return 0;
}
\end{lstlisting}

\section{Answers to Required Observation Questions}
\begin{enumerate}
    \item \textbf{File Descriptor Allocation Mechanics (Why Descriptor 3?):}
    \begin{itemize}
        \item Under POSIX operating systems, every process is initialized with three pre-allocated standard streams:
        \begin{itemize}
            \item \texttt{0} --- Standard Input (\texttt{stdin});
            \item \texttt{1} --- Standard Output (\texttt{stdout});
            \item \texttt{2} --- Standard Error (\texttt{stderr}).
        \end{itemize}
        \item The Linux kernel follows a strict **lowest-available-index allocation policy** for process file descriptor tables (\texttt{struct files\_struct}). When \texttt{open()} is invoked, the kernel scans the table starting from index 0 and assigns the first free numerical slot.
        \item Since slots 0, 1, and 2 are already assigned to terminal descriptors upon process initialization, the first available index is **\texttt{3}**.
        \item When \texttt{close(3)} is called, slot 3 is released. Consequently, the subsequent \texttt{open("note.txt", O\_RDONLY)} reallocates slot **\texttt{3}**.
    \end{itemize}

    \item \textbf{Relationship Between \texttt{printf()} and \texttt{write()}:}
    \begin{itemize}
        \item \texttt{printf()} is a user-space library function implemented in the C runtime library (\texttt{glibc}). It provides string formatting and user-space memory buffering.
        \item \texttt{write()} is the underlying kernel system call that transfers raw bytes across the user-kernel privilege boundary.
        \item As seen in Figure 3.2, calling \texttt{printf("open returned descriptor 3\textbackslash n", fd)} does not execute in kernel space directly; instead, \texttt{glibc} formats the string into a buffer and immediately invokes \texttt{write(1, "open returned descriptor 3\textbackslash n", 27)} to flush the line to descriptor 1.
    \end{itemize}
\end{enumerate}

\chapter{ANALYSIS OF KERNEL-USER BOUNDARIES}

\section{System Call Dispatching Architecture}
On the x86\_64 Linux architecture, the transition from unprivileged userland to privileged kernel mode proceeds through the \texttt{syscall} machine instruction:
\begin{enumerate}
    \item \textbf{Register Setup:} User-space wrappers load the system call number into register \texttt{rax} (e.g., \texttt{rax = 1} for \texttt{SYS\_write}, \texttt{rax = 257} for \texttt{SYS\_openat}). Call parameters are loaded sequentially into registers \texttt{rdi}, \texttt{rsi}, \texttt{rdx}, \texttt{r10}, \texttt{r8}, and \texttt{r9}.
    \item \textbf{Privilege Transition:} The CPU executes the \texttt{syscall} instruction. The hardware transitions from Ring 3 to Ring 0, saves the instruction pointer into \texttt{rcx}, and jumps to the kernel entry point recorded in the Model Specific Register \texttt{IA32\_LSTAR}.
    \item \textbf{Dispatcher Execution:} The kernel entry stub pushes user registers to the kernel stack, checks the system call number against the architecture jump table (\texttt{sys\_call\_table}), and executes the corresponding service routine (such as \texttt{ksys\_write()}).
    \item \textbf{Return to Userland:} Upon completing the request, the return value or negative error code is placed into \texttt{rax}, and the \texttt{sysretq} instruction restores user-space execution.
\end{enumerate}

\section{The Role of \texttt{strace} and \texttt{ptrace}}
The \texttt{strace} utility attaches to the target process using the \texttt{ptrace(PTRACE\_SYSCALL, ...)} primitive. The kernel suspends the traced process twice per system call: once immediately before syscall entry (allowing inspection of arguments), and once immediately following syscall exit (allowing inspection of return values). This architecture ensures that every transition is captured without altering application source code.

\chapter{CONCLUSIONS}
In this laboratory work, the low-level communication interface between user-space applications and the Linux kernel was analyzed using the \texttt{strace} diagnostic utility.

Executing \texttt{ls -l} under syscall interception demonstrated that standard utilities depend on basic kernel primitives (\texttt{openat}, \texttt{getdents64}, \texttt{write}) for resource discovery and data rendering. Developing \texttt{syscalls.c} confirmed that file descriptor allocations follow a deterministic lowest-index policy starting at descriptor \texttt{3}, and demonstrated that standard formatting functions (\texttt{printf}) are user-space abstractions that delegate directly to \texttt{write()}. 

The experiment highlighted the structural separation of privilege rings, reinforcing the role of the operating system kernel as the sole arbitrator of hardware resources.
